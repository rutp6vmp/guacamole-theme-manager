PAM 獨立啟動檢查、受保護入口與安全持續性驗證
處理日期：2026-10-31（Asia/Taipei）
版本：session probe 0.4.0；Guacamole 1.6.0；單 Web/JDBC/SSH；localhost 隔離試驗。
對應：F04-01/02、X19-03/04/06、X22-03、G04-01/02、P00、J/L。
本輪延續原規劃「模組遺失時不能靠該模組保護自己」的要求。

一、實作方向與信任邊界

1. bootstrap.sh 是安全 JAR 之外的獨立檢查，先確認明確的 fixture-only opt-in、
   操作者釘選的 SHA-256、一般非 symlink 模組檔，再 exec 原版官方 entrypoint。
   缺檔、雜湊改變、缺 pin 或任意啟動命令都以 exit 78 拒絕，不啟動 Tomcat。
   這是本原型的安裝前提檢查，不是數位簽章或可信發行者認證。

2. NGINX 位於唯一 published port，Web/DB/guacd/SSH 都不 publish host port。
   每個新 HTTP 請求在轉送前，以 auth_request 查詢同一個私有 Web 的 provider readiness。
   靜態首頁、登入 POST、REST、HTTP tunnel 與 WebSocket Upgrade 都走同一個 location。
   readiness 不存在、503、連不上、timeout 或其他非預期回應，均不轉送原始請求。
   不快取成功的 readiness，不接受瀏覽器 header 當作模組、身份或 MFA 證據。

3. provider 的公開資源 GET /guacamole/api/ext/pam-session-probe/ingress-ready
   僅在 fixture-only、已配置政策檔且 durable policy/checkpoint 健康時回空白 204，否則 503。
   沒有 username、token、檔案路徑、SHA、generation 或完整連線參數回應。
   它只證明此 Web 目前載入提供者並能讀取原型政策，不是 grant/身份/MFA/DB 健康證明。

4. 伺服器 connect gate 保留既有的身份 context、一次性 intent、原生權限與 policy 重查。
   入口檢查不代替這些授權；健康的入口也不代表任意使用者可以直接連受控資產。
   原型只允許合成 gtm-* JDBC 身份，不能當作正式 vendor_access_enabled 功能。

使用者尚無正式網域/HTTPS；本輪沒有對外啟用、改正式 Compose/CLI/帳號/登入或重建正式容器。

二、原創來源與設定

modules/guacamole-adapter-1.6/ingress-probe/bootstrap.sh
modules/guacamole-adapter-1.6/ingress-probe/nginx.conf
modules/guacamole-adapter-1.6/session-probe/src/main/java/
  org/guactheme/pam/sessionprobe/SessionProbeProvider.java

bootstrap 使用 PAM_SESSION_PROBE_REQUIRED_SHA256 取得可信部署設定提供的 64 位小寫 hex。
預設讀 /etc/guacamole/extensions/guacamole-pam-session-probe.jar；測試或不同安裝可用
PAM_SESSION_PROBE_EXTENSIONS_DIR 指定絕對路徑。該設定由部署者提供，不從 HTTP 讀取。
--check-only 僅核對停止中的檔案，不啟動服務；runtime 只接受官方 entrypoint 一個命令。
無 force/bypass、自動換 pin 或自動下載／替換安全 JAR 的功能。
Compose 明確提供 entrypoint 及 command，保留官方 /opt/guacamole/bin/entrypoint.sh 的完整初始化。

NGINX fixture 使用 nginx:1.28.0-alpine；不是系統全域安裝。
nginx.conf 以 Docker DNS 解析單一 web:8080，沒有硬編碼主機 IP、正式網域或公開埠。
valid=1s 讓 Web 重建後重新解析；這不是多實例負載平衡或跨節點健康證明。
內部 auth subrequest 不轉送 body、Cookie、Authorization 或 Guacamole-Token。
入口無 access log，error log 不記錄一般請求，以免原生 tunnel query 帶的 bearer token 落盤。
封鎖回應為固定的 503 與 no-store，不把原生錯誤、路徑或秘密回給入口使用者。

已 Upgrade 的 WebSocket 不再是新的 HTTP 請求，NGINX 不會逐 frame 重新 auth_request。
已連 primary 的有界期限仍由 provider 本地 lease 執行；不能把政策變壞說成代理立即中斷所有活動 tunnel。
模組檔在磁碟被移除時，已載入的原本程式可能仍在記憶體；下次啟動會被 bootstrap 拒絕。

三、實際驗收與恢復方式

tests/ingress_acceptance.py 沿用 session fixture 的隨機 project、合成密碼與真實 OpenSSH。
先將原 localhost port 移交 entry，取消 Web publish，再建立 readonly bootstrap/config 掛載、
唯讀政策目錄及獨立私有 checkpoint。所有操作只使用該新 project 的完整 Compose 清單。
不接受正式環境路徑作目標，也不因故障刪除其他擴充或修改 WAR。

驗證情境：
1. 健康入口可登入，HTTP/WS 都執行真實 SSH；runtime 沒有 Web/DB/guacd/SSH bypass publish。
2. 必要政策檔缺失，首頁、登入 POST、REST、HTTP/WS 新 tunnel 皆封鎖，偽造 header 無效。
3. 既有 Upgrade 的 WebSocket 最後仍由本地 lease 關閉；恢復較高 generation 後入口恢復。
4. 安全模組缺失及內容被改，bootstrap 都阻止官方 entrypoint，入口保持封鎖。
5. 私有負面對照刻意省略 bootstrap 及 JAR，原生 Web 實際正常啟動、登入並可連 SSH；
   同一時刻 entry 仍封鎖原生登入、REST 與兩種 tunnel，證明不是因 Web 沒起來才拒絕。
6. 還原釘選的 JAR、bootstrap 與有效政策，重新登入和 fresh intent 才能經 entry 連 SSH。
7. 將同一完整 Compose 清單與 module pin 交給 protect-deployment；主題操作後繼續核對入口保護。

管理者透過 Docker 私有網路直接操作後端是高信任的測試／救援通道，不是外包入口。
本機負面對照讀取隨機 fixture 的 bridge IP，因此這套測試目前以 Linux Docker bridge 驗證。
主機／Docker 管理員有權修改掛載、pin 或網路，不在此原型的防竄改邊界。

五、保留缺口與後續方向

G04 保留部分通過：尚無正式 external_enforced profile、HTTPS、可信代理政策及外包最低能力總檢查。
模組 availability 不代表 MFA freshness、正式 grant/錄影/IdP/DB/worker 都健康。
readiness 與轉送要到同一 Web；HA/rollout/多 backend 場景需 instance 綁定或獨立證明。
不能把此樣板直接擴成 round-robin，讓 A 的健康替 B 的缺模組放行。
仍需正式部署／升級／pin 變更程序、TOTP/錄影/所有工具的完整安全連續性與多協定驗收。
所有觀測僅為本機單次驗證，不構成 SLA；閘道斷線仍不保證目標 OS 登出或背景程序終止。
