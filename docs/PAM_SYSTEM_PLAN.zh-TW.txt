01. 產品定位與原創實作原則
======================================================================

暫定產品結構：GuacTheme Manager（獨立視覺工具）＋ GuacPAM Core（暫名，安全控制模組）。
最終名稱尚未決定；不得因暫名而自動改掉現有產品名稱、repository 或 namespace。

核心目標是控制以下生命週期：
誰／代表哪家廠商 → 為何要存取 → 哪個資產與目標帳號 → 誰批准 → 有效多久 →
如何建立工作階段 → 執行時如何限制與追溯 → 何時撤權／中斷 → 憑證如何保護及輪替。

原創範圍：PAM 領域模型、政策規則、狀態機、審批流程、對外契約、管理介面、
稽核關聯與部署工具自行設計；不複製商業 PAM 的原始碼、專有 API、商標或介面素材。
可以使用依法授權的 Guacamole 與成熟標準函式庫，須維護 LICENSE、NOTICE 與依賴清單。
不自行發明密碼學、OTP 演算法、加密協定或密碼庫格式來追求「原創」。

Guacamole 繼續負責遠端協定與基本身份認證；PAM 負責特權使用政策與生命週期。
Guacamole 帳號、目標設備上的 root／Administrator／維運帳號、以及 PAM 的應用角色，
必須是三種分開的概念，不得用同一個「管理員」欄位混在一起。

第一版的 JIT 指「限時允許使用遠端連線」；不等於已在目標 Windows／Linux 上
臨時新增管理員權限。主機上的提權、sudo、JEA 或端點權限管理，屬後續獨立整合。

02. 對外開放條件與安全邊界
======================================================================

建議先以單一客戶／單一安裝環境為產品基線，環境內可有多家廠商。
「廠商組織隔離」不等於已具備跨客戶 SaaS 多租戶能力；對外不得混用兩者宣稱。
需要多客戶時，第一階段優先採不同安裝實例、資料庫與金鑰；共用服務須另外驗證隔離。

外包正式開放的最低條件：HTTPS、每人獨立身份、MFA、內部負責人、合約／帳號期限、
廠商與資產隔離、伺服器端授權檢查、可追溯的工作階段、撤權機制與管理員復原流程。
只完成 MFA 或錄影的階段，可先做內部試點，不代表已通過完整外包接入驗收。

主要信任邊界：
1. 瀏覽器及其 Local Storage 不可信；角色、MFA 狀態、組織與授權期限由伺服器判定。
2. 反向代理只信任明確列出的上游，不能接受任意客戶端偽造 Forwarded／X-Forwarded-*。
3. guacd 與目標管理網路不對外公開；外包來源不能直接繞過閘道連到目標。
4. Guacamole 的原生連線入口、HTTP tunnel、WebSocket、重連、共享與負載平衡路徑，
   都需要接受同一政策；只把按鈕藏起來不算安全控制。
5. PAM 管理者不自動成為目標主機管理員；錄影稽核員不自動取得密碼或連線編輯權限。
6. 主機 root、資料庫管理者及保管庫管理者屬高信任管理平面；本產品不能宣稱防住
   已完全掌控宿主機的 root。須靠職責分離、外部稽核與基礎設施保護降低風險。

必測攻擊情境：跨廠商猜測 ID、自己批准自己、舊授權重放、到期前後併發啟動、
換瀏覽器／換帳號轉交入口、原生 URL 繞過、權限快取未失效、政策服務失聯、
時鐘異常、錄影下載越權、MFA 重設濫用、憑證出現在回應／日誌／匯出檔。

03. 角色、組織與權責
======================================================================

平台管理員：安裝、升級、備份、健康檢查；不因平台角色自動核准所有維運需求。
安全管理員：維護政策、MFA 例外、敏感存取規則、緊急復原與安全設定。
資產負責人／審批者：只審批自己負責的資產與指定廠商範圍。
內部維運者：依政策申請及使用授權；若需長期例外，須有明確範圍與定期複核。
外包維運者：只見所屬廠商、有效合約與被允許申請的設備；不取得全域管理權。
廠商聯絡人：協助提出人員異動，不得自行發放目標存取權或重設所有人 MFA。
稽核員：查閱被授權的事件、歷史及錄影，觀看與匯出分開授權。
緊急復原管理者：使用獨立管理通道及程序，事後必須留下原因與複核記錄。

角色採「動作＋資源範圍＋條件」模型，不能只靠角色名稱授權。
例如：approve_request，範圍為某環境／資產群組，條件為非申請者本人且仍為負責人。
同一人可因小型組織需要兼任角色，但系統仍應阻擋自我審批與越權。
角色、組織成員或合約異動，要立即影響後續授權判斷，不能等下一次登入才更新。

04. 技術架構與擴充邊界
======================================================================

建議資料流：
瀏覽器 → HTTPS 入口 → Guacamole 身份認證／MFA → PAM 管理 API →
政策及授權資料 → Guacamole 伺服器端連線檢查 → guacd → 指定目標。
工作階段事件 → 稽核／錄影索引；撤權／到期事件 → 檢查與中斷控制。
保管庫與通知透過受控 connector 整合，不直接交給瀏覽器呼叫。

優先採模組化單體：原創 Java 領域核心＋版本專用 Guacamole Java extension adapter，
利用既有 Web／PostgreSQL 基礎設施。先用受控的背景工作與資料庫工作佇列，
沒有量測需求前不加入 Kafka、Redis、Kubernetes 或多套微服務框架。

若 G01～G03 證明內嵌擴充無法安全處理身份綁定、背景工作生命週期或部署隔離，
才以 ADR 記錄證據，改採一個小型控制服務；不能只因熟悉某框架就新增後端。
即使分離服務，接近 Guacamole tunnel 的政策執行點仍不可省略。

模組責任：
Domain：身份範圍、政策判斷、申請、審批、授權及狀態轉移，無 Guacamole 前端依賴。
Guacamole adapter：身份對應、目錄／權限限制、連線前檢查、工作階段追蹤及撤銷。
PAM API：驗證請求、取出已認證主體、執行服務層、遮罩回應與留下操作稽核。
UI：顯示目前使用者可見的資料及可執行動作；不得自行作最終授權判定。
Jobs：到期處理、撤權重試、錄影結算、保留政策、通知及狀態對帳。
Connectors：身份、憑證庫、錄影儲存、通知、稽核輸出與未來目標改密。

04.1 已核對的 1.6.0 Java 接入點（仍須做端到端 POC）
AuthenticationProvider.decorate(...)／redecorate(...) 可包裝其他 provider 的 UserContext。
Connectable.connect(GuacamoleClientInformation, Map<String,String>) 回傳 GuacamoleTunnel。
Connection、ConnectionGroup 及 ActiveConnection 的不同路徑，都要納入檢查。
UserContext.getActiveConnectionDirectory()、ActiveConnection.getTunnel() 及
GuacamoleTunnel.close() 是工作階段控制的候選接入點。
Directory.remove(identifier) 的權限與效果，必須以實際 provider 驗證，不能假設會終止
所有節點上的工作階段，也不能把 close tunnel 說成已登出目標 OS 或停止遠端背景程序。

已核對原始碼基準：apache/guacamole-client tag 1.6.0，
commit 0537c89cd783681b986ff8f8c4e0b97ec6873371。
前端 Angular services／DOM 屬版本綁定的內部實作；不得宣稱為跨版本公開 API。
安全邏輯放在伺服器端，不能建立在前端 controller 或 Local Storage 上。

05. F01 身份與外包廠商生命週期
======================================================================

輸入：廠商名稱、內部負責人、合約起訖、聯絡方式、使用者身份來源及申請範圍。
輸出：可追蹤的廠商／人員狀態及有效期限，不直接等於已批准設備連線。

廠商狀態：DRAFT → ACTIVE → SUSPENDED／EXPIRED → ARCHIVED。
人員狀態：INVITED → PENDING_ENROLLMENT → ACTIVE → SUSPENDED／EXPIRED／REVOKED。
正式申請需有有效廠商、有效人員與有效內部負責人；失效時由後端拒絕新連線。

每人獨立帳號，不使用多人共用的「vendor」登入帳號。
身份主鍵採穩定的身份來源＋subject／provider identifier，顯示帳號或 Email 變更不得
把舊授權誤送給新使用者。資產引用同樣使用 installation＋data_source＋connection_id。
廠商 A 不得透過更換 URL、JSON vendor_id 或篩選條件取得廠商 B 的資料。

加入流程：內部負責人建立邀請 → 人員身份確認 → 設定登入及 MFA → 確認有效期限 →
授予可申請的資產範圍。邀請碼需一次性、短期、可撤銷，不能存明文或寫入存取日誌。
邀請、密碼重設與 MFA 重設是不同操作；廠商聯絡人不能因此得到安全管理員能力。

離場流程：立即禁止新申請／連線 → 撤銷尚未使用的啟動資格 → 撤銷有效授權 →
依政策中斷既有工作階段 → 停用身份 → 處理憑證／錄影保留與未結案件。
同時記錄操作者、原因、影響範圍及未能完成的中斷／回收項目。
內部負責人離職或失去角色時，案件須轉交或停用，不自動放寬廠商權限。
PAM 組織關係停用與身份來源的帳號停用分開處理；若同一身份也用於其他內部業務，
不得因廠商合約結束就誤停全公司身份。對 IdP 的寫入需有明確的 provisioning 範圍。

驗收：跨組織 IDOR、改名、帳號重用、合約到期、批次停用與有活動連線時離場。

06. F02 資產、目標帳號與操作能力
======================================================================

資產資料：穩定引用、顯示名稱、分類、協定、環境、擁有者、風險層級、可申請廠商、
允許時段、錄影要求及支援的操作能力。秘密內容只存 provider reference，不存於清單。
現有 Guacamole 連線與群組先透過授權 API／UserContext 盤點，不直接掃描私有 DB 欄位。
名稱與協定不能當成真正作業系統、設備健康或風險分類的可靠證據。

目標帳號另建模型：個人帳號／共用維運帳號／服務帳號、用途、資產、擁有者、
保管庫引用、可輪替能力、特權層級、啟用狀態及已確認的 credential version。
「可連線」不自動代表可編輯 hostname、查看 password、建立共享連結或變更協定。
外包及一般維運者原則上只有使用權，不授予原生連線 UPDATE／ADMINISTER 權限。

1.6.0 原生參數端點可向具連線 UPDATE 或系統 ADMINISTER 的使用者回傳參數；
目前主題的 hostname 顯示也遵循此權限。因此原有編輯者不能直接被視為「看不到密碼」
的 PAM 操作者。須重新定義角色，並驗證保管庫及 adapter 不向參數端點洩漏秘密。

能力設定：剪貼簿讀／寫、檔案上／下載、磁碟／SFTP、唯讀、分享、閒置及最長時限。
不同協定支援不同能力；adapter 要提供 capability matrix，支援才開放設定。
當政策要求的限制無法在後端生效時，拒絕啟動並顯示不支援，不能靜默忽略。
操作人不能提交任意 hostname／port 來把 guacd 變成通往未核准設備的跳板。

07. F03 身份保護、MFA 與復原
======================================================================

第一階段重用官方 TOTP extension，不重寫 OTP 演算法。1.6.0 可透過 TOTP_ENABLED
啟用；官方預設為 6 位數、30 秒、SHA-1。金鑰保存依賴支援擴充屬性的身份後端，
現有資料庫認證可作候選。首次登入須由使用者在自己的驗證器完成綁定。[R1]
1.6.0 有個別使用者／群組停用 TOTP 的功能；這是需要管理的例外，不是預設通行證。

設計流程：先驗證原有身份 → 要求註冊或驗證第二因素 → 後端確認因素達標 →
才允許進入受保護資產流程。綁定未完成不得視為已啟用；變更裝置要走重設程序。
QR code、seed、otpauth URI、驗證碼與登入 Token 不得進入日誌、截圖、Git 或報表。
測試只能使用新建的合成帳號與測試金鑰，且清理後不可再使用。

外包與一般使用者不得自行取消 MFA、降低驗證因素或藉群組例外繞過。
務必測試原生屬性編輯權限；如果原生設定無法滿足角色限制，需伺服器 adapter 補足，
不得只隱藏勾選框。信任 SSO 的 amr／acr 時，要限定 issuer、audience、簽章與
新鮮度；「IdP 已做 MFA」必須有可信證據，不能相信瀏覽器傳來的布林值。

復原流程：驗明身份、重設理由、授權管理者、一次性處理、完整稽核及必要的再次綁定。
優先由另一名已具 MFA 的安全管理員重設單一使用者，不預留永久免 MFA 的外包群組。
最後手段的伺服器端緊急停用，須先限制外部入口、設定維護期限與復原責任人；
不能把 MFA 關閉後仍標示系統受到同等保護。

驗收：首次綁定、錯碼、過期碼、官方支援範圍內的重放行為、裝置遺失、管理者也被
鎖住、群組例外、時間漂移、SSO 重新認證及啟用／停用後的回復。
不在正式 DB 直接塞入自製 TOTP seed 或以聊天中的密碼代替帳號持有者綁定。

08. F04 HTTPS、外部入口與網路隔離
======================================================================

外包入口要求受信任的 HTTPS；正式入口不直接暴露未保護的 Web port 或 guacd。
支援 WebSocket upgrade、合理的 request／idle timeout、速率限制與來源資訊傳遞。
代理信任清單、應用 base path、公開 URL 與內部 upstream 必須是可設定項。
原始 Guacamole API／tunnel 同樣受保護；不能只保護 PAM 首頁卻保留另一個未控管入口。

IP allowlist 是附加條件，不替代身份與 MFA。外包共用 NAT 不能被當作同一人。
所有日期保存 UTC，前端可用 Asia/Taipei 或使用者時區顯示，邊界比較使用伺服器時間。
Guacamole、PAM、保管庫及目標的時鐘同步狀態須納入健康檢查。

一般瀏覽器防護：安全 Cookie、CSRF、防止不受信任 CORS、輸出編碼、上傳限制及
避免 URL／Referer 洩漏 bearer token。具體實作需配合既有 Guacamole 身份流程驗證。
後續加入外部 IdP 時，需測試登出、撤銷與 token 到期，不只測首次登入。

======================================================================
09. F05 工作階段錄影與證據保存
======================================================================

官方 1.6.0 支援工作階段錄影及瀏覽器回放，錄影可透過 history UUID 對應歷史。[R2]
應先建立 protocol-specific 錄影／儲存能力矩陣，再決定 RDP、SSH、VNC 的具體參數。
不能以「有歷史記錄」代替「錄影成功」，也不能把錄影檔存在視為證據保存已完成。

每個 session 須對應：申請、grant、個人身份、廠商、資產、目標帳號引用、開始／結束、
原因、節點、錄影模式、檔案狀態、摘要與保存政策。檔名使用伺服器生成的 opaque ID。
建議狀態：PENDING → WRITING → FINALIZING → AVAILABLE／FAILED → PURGED。
異常退出或不完整檔案標示為不完整，不可顯示「完整錄影已保存」。

儲存路徑參數化；guacd 取得必要寫入權，Web／播放服務採最小讀取權。
存放區不能是公開靜態目錄；回放、下載、匯出及分享都要再次檢查身份與資產範圍。
原生錄影可見性和歷史權限有關，必須驗證其是否符合廠商隔離；若不符合，需由
伺服器 adapter／受控播放 API 限制原生端點，不能只過濾前端列表。

鍵盤事件記錄預設不啟用，除非明確政策與告知需要；即使不記鍵盤，畫面也可能含
密碼或業務資料，不能宣稱會自動遮罩全部秘密。觀看與下載採不同權限並留下稽核。
定義保存期限、每組織 quota、磁碟預警、法律／事件保留標記及刪除工作。
建議一般保存 90 天僅是待確認預設，不代表任何特定法規要求。

對「強制錄影」的資產，錄影準備失敗須拒絕新連線；途中失敗時依政策中斷並告警。
不能只看路徑可寫就保證 guacd 實際寫入，需觀測與測試檔案建立、成長、結算及容量。
若要容許不錄影例外，需事前核准且標示風險，不能默認降級。

驗收：三種協定實際目標、播放、跨廠商禁止讀取、長連線、磁碟滿、檔案截斷、
節點重啟、時間關聯、保留鎖及資料刪除。普通 SHA-256 只能協助完整性校驗，不能
單獨宣稱可抵抗宿主機 root／DB 管理者竄改。

======================================================================
10. F06 存取申請與原創審批流程
======================================================================

申請欄位：個人身份、廠商、資產／固定資產集合、目標帳號引用、用途、工單參考、
預計開始與結束、需要的剪貼簿／檔案等能力、是否需要緊急處理。
不讓申請者自行指定核准人、MFA 達標狀態、最終風險級別或無限期有效。

申請狀態：
DRAFT → SUBMITTED → UNDER_REVIEW → APPROVED／REJECTED／CANCELLED／EXPIRED。
核准是決定紀錄，不直接代表目前可用；實際 grant 仍要檢查時間、合約、身份及政策。

後端根據資產擁有者、環境、風險與廠商，自動建立審批路線快照。
預設非本人單一審批；高風險可採資產負責人＋安全管理員兩階段，規則可設定。
一人兼任兩角色時是否可算兩階段，不可默認；建議仍要求兩個不同的人。
負責人異動、審批者失去角色或合約範圍改變時，需要重新評估未結案件。

審批人可縮短時段、縮小資產範圍或降低能力；增加權限／延長時間需形成新的申請
或有版本的重新審批，不能悄悄修改已核准內容。核准畫面顯示實際授予的差異。
同時核准／駁回以資料庫版本號與交易鎖保護，只允許一個有效轉移。
記錄誰在什麼角色及範圍下決定、理由、時間、政策版本與原始請求版本。

內部自動核准可作明確政策：僅限指定內部角色、低風險資產、短時段及稽核完整。
外包不預設自動核准；緊急流程也不能由外包自行按「緊急」取得高權限。
通知先用站內；Email／工單系統是可選 connector，送出失敗不改變審批的真實狀態。

驗收：自我審批、偽造 approver、跨資產核准、雙擊及併發、過期審批、角色撤銷、
改動已核准請求、工單欄位注入及通知重送。不得以 UI 的按鈕停用作為唯一防護。

======================================================================
11. F07 限時授權與連線前執行點
======================================================================

grant 是不可任意擴張的已核准權利：subject、vendor、asset_ref、target_account_ref、
not_before、expires_at、max_session_duration、max_concurrent_sessions、能力、policy_version。
使用半開區間 [not_before, expires_at)，避免邊界秒出現兩種判斷。
grant 狀態：SCHEDULED → ACTIVE → EXPIRED／REVOKED／EXHAUSTED。

政策基本公式：
允許 = 可信身份有效 AND MFA 達標 AND 組織／合約有效 AND 原生必要權限有效
       AND 資產在範圍內 AND 核准仍有效 AND 時間符合 AND 未撤銷
       AND 併發／能力／錄影等條件符合。
任何一個必要條件不成立即拒絕。前端倒數僅作提示，伺服器時間才是依據。
歷史快照供追溯，不豁免目前的強制安全政策。政策收緊後要重新判斷有效 grant／session；
政策放寬也不自動擴大舊 grant，新增能力仍需相應的核准。

啟動流程：
1. 已認證使用者提出啟動意圖；後端從可信 session 取得身份，不相信 body 中的 user_id。
2. 原子檢查 grant 及併發容量，產生短期、一次性的 admission／launch intent。
3. Guacamole 伺服器端 adapter 在真正 connect 前重新檢查並消耗啟動資格。
4. 建立 session lease，記錄最早結束期限，然後才交由 guacd 連線。
5. 失敗時安全釋放容量，記錄原因；不能因 HTTP 重試重複扣額度或建立多條連線。

啟動證明至少綁定主體、安裝／組織、資產、grant、期限、隨機 nonce 與安全政策。
若需要綁定特定登入 session，G01 必須先證明可從可信介面取得該 session 參照。
不得用單純 username、可偽造的 HTTP header 或前端變數假裝完成 session 綁定。
建議啟動資格 60 秒內到期；這是可調整的設計值，不是 Guacamole 原生參數。

G01 的實作候選：受控的暫時連線識別碼／provider，或可被 adapter 安全讀取的
伺服器端 admission store。必須以實際 1.6.0 路徑證明，不先假設有自訂 launch API。
Base64 client ID 不是秘密；複製 URL、改 data_source、使用原生入口或繞過 PAM UI，
均不能取得未核准連線。合法原生入口是否仍允許，需採同等後端檢查且保持稽核關聯。

對受控資產，即使使用者在原生 Guacamole 有 READ，也不能因此跳過 PAM gate。
不得為了方便連線，把 ADMINISTER／UPDATE 或管理員 token 發給外包瀏覽器。
若以既有 READ 權限作底層基礎，要同時阻擋所有未經 gate 的原生旁路。
原生權限與 PAM 授權採交集；自動擴增底層權限是另需審查的 provisioning 流程。

負載平衡群組須檢查實際選出的資產與帳號；不能核准一個群組就默默授權未來加入的
所有設備。共享／加入活動連線同樣要有自己的身份與有效授權，初版可先禁用外包共享。

驗收：未核准、未到開始時間、剛好到期、重放、跨身份、不同 provider 同 ID、
雙瀏覽器併發、政策變更、原生 URL、WebSocket／HTTP fallback、群組與共享旁路。

======================================================================
12. F08 工作階段控制、到期與撤銷
======================================================================

session 狀態：STARTING → ACTIVE → TERMINATING → ENDED／FAILED。
另記 termination_requested_at、termination_confirmed_at、reason 及執行節點。
租約期限取 grant 到期與工作階段最大時長的較早者；閒置期限是另一個獨立限制。

撤銷後立即拒絕新的啟動及重連；對活動 session 發送中斷並由背景工作重試／對帳。
建議活動 session 撤銷／到期中斷的初始目標為 15 秒內，實際數字須經量測與政策確認。
不能在排程工作尚未成功關閉 tunnel 時，就把資料列改成「已成功終止」。
PAM API／worker／Web 節點失聯時，新連線採 fail closed；活動 session 需有本地硬期限
及有限的撤權檢查週期，不能因控制平面故障永久延長。可用性與中斷策略須明文可設定。
多節點時記錄 node_id、owner lease、heartbeat 與 fencing version，失去所有權的舊
worker 不得繼續操作。只有完成跨節點實測，才宣稱支援叢集與即時撤權。

第一版斷線／中斷指停止閘道工作階段，不保證目標 OS 已登出、RDP logon session
被刪除，或已執行的背景程序停止。需要目標登出／程序控制時，須有另行授權的 connector。
監看、唯讀旁觀與接管也是不同動作；未有可靠支援前，不提供假按鈕或只改畫面的「唯讀」。

驗收：grant 到期、手動撤銷、廠商停用、閒置、重連、worker crash、Web restart、
控制平面中斷、重複終止命令、延遲事件及分散式時鐘偏差。不得誤殺無關使用者的連線。

======================================================================
13. F09 憑證保管與安全注入
======================================================================

第一步採外部保管庫 connector，領域資料只保存 secret reference 與版本引用。
Guacamole 1.6.0 的官方 vault 擴充文件明列 Keeper Secrets Manager；其他 provider
不得宣稱直接相容，須自行完成 connector 契約、授權及端到端測試。[R3]

只在核准且即將建立連線時，由後端依最小權限取得必要秘密並注入連線。
操作人看到資產／帳號顯示名稱即可；瀏覽器、一般 API、CSV、錯誤頁與錄影索引不回傳秘密。
測試 getConfiguration、原生參數端點、複製連線、分享與匯入／匯出等路徑是否洩漏。
保管庫取密失敗、版本不明或權限不足時拒絕啟動，不退回硬編碼密碼或舊快取秘密。
注入與能力限制必須是 per-session，不能修改多使用者共用的 Connection 物件或把秘密
寫回原生連線設定。token map 是否被特定 provider 採用，必須實測，不能只因介面有參數
就假設已成功注入；無法可靠落實時拒絕該能力或改用已驗證的 adapter。

每個 connector 需定義 getVersionedSecret、health、能力及錯誤類別；秘密回傳類型
應阻止一般 toString／JSON 序列化。記憶體停留時間盡量縮短，不宣稱 JVM 能保證抹除所有副本。
保管庫應用憑證以受保護檔案／secret mount 等方式提供，與一般設定分離。
Docker inspect／宿主機管理者的能力須列入威脅模型，不能因改用環境變數就宣稱安全。

本機假 provider 只用於自動化測試與 localhost demo；正式 profile 必須拒絕測試秘密。
若未來需要內建 vault，須獨立安全設計與外部金鑰管理，不能將一個 AES helper 當成完整 vault。

======================================================================
14. F10 密碼輪替與目標提權（後續階段）
======================================================================

目標 connector 必須提供能力聲明：支援的 OS／設備／帳號種類、驗證方式、改密、
是否可復原及需要的管理權限。SSH、RDP 是連線協定，不代表已能對所有設備安全改密。

輪替狀態：PREPARED → APPLYING_TARGET → VERIFYING_TARGET → COMMITTING_VAULT →
SUCCEEDED，或 FAILED_RECONCILE_REQUIRED／QUARANTINED。
這是外部系統的分散式流程，不是資料庫單一交易，必須有對帳及人工處置方向。

同一憑證採排他鎖；先確認救援通道與版本，再執行目標變更及驗證。
目標已改密但 vault 寫入失敗時，新的秘密需受保護地保留供復原；不能遺失，也不能
把未確認版本當作已完成。舊密碼可能因歷史限制不能改回，不可承諾永遠能簡單 rollback。
禁止把密碼放在命令列、shell interpolation、程序參數、工單或 stderr。

使用後改密應以「該 credential 最後一個相關工作階段結束」判斷，處理同時使用、
強制撤銷及異常斷線。既有 tunnel 與新啟動的憑證版本要分開記錄。

主機提權另設 PrivilegeElevationProvider：例如特定 sudo 任務或受限制的 Windows 操作。
先建立可驗證的 capability，避免把整個 root／Administrator 帳號稱作最小權限。
SSH 命令管制若無可靠伺服器／目標執行點，不可用前端字串黑名單冒充。
初期不宣稱覆蓋所有 GUI 動作、所有 shell 逃逸或所有端點權限管理需求。

15. F11 稽核、報表、通知與證據鏈
======================================================================

稽核事件至少包括：登入／MFA 成敗、邀請與離場、角色／政策變更、申請／審批、
啟動允許／拒絕、session 開始／結束、撤權、錄影觀看／下載／刪除、憑證取用／輪替、
緊急復原、設定／升級／備份／還原。

事件欄位：event_id、installation_id、UTC 時間、actor_ref、vendor_ref、asset_ref、
request_id、grant_id、session_id、correlation_id、policy_version、動作、結果及原因碼。
client IP 只在可信代理鏈成立時記錄；敏感輸入不原樣寫入，帳密／token 永不放在事件中。

交易性變更和 audit／outbox 應在同一 DB 交易中提交，避免「已核准但沒有稽核」。
背景輸出採至少一次傳送＋event_id 去重；通知重試不能重複核准或重發有效權限。
不可重建關鍵稽核時，對高風險新操作採拒絕或明確的維護政策，不靜默繼續。

提供依時間、廠商、身份、資產、申請、工作階段、結果的查詢，套用同等後端範圍限制。
匯出要有限量、到期、再次授權及事件記錄；不能發出永久公共錄影／CSV 連結。
輸出 CSV 須處理公式注入；Email／工單內容不夾帶秘密、QR code 或長期 bearer URL。

DB append-only 權限、hash chain 與外部定期 anchor 可分階段導入；只有實際具備
外部可信錨點／不可變儲存與驗證程序時，才可宣稱對相應威脅具防竄改能力。
稽核保存期與錄影保存期分開設定；事件保留鎖、敏感資料存取及刪除行為也要可追溯。

16. F12 原創產品介面與操作流程
======================================================================

沿用現有主題配色機制與繁體中文／英文命名空間，新增 PAM 頁面採自己的資訊架構：

我的工作台：可申請資產、目前授權、到期倒數、自己的工作階段與待補資料。
我的申請：新增申請、顯示實際範圍、狀態、決定理由、取消與重新申請。
待我審批：顯示責任範圍、風險、時段與能力差異；後端重新檢查審批者資格。
廠商與人員：合約、負責人、有效期限、邀請／停用及未結案件。
資產與目標帳號：責任人、風險、協定能力、憑證引用；不顯示秘密內容。
授權與工作階段：可用／未生效／過期／撤銷、活動狀態、真正的中斷結果。
稽核與錄影：事件關聯、授權回放、有限下載、保存狀態及缺失提示。
安全與整合設定：MFA 政策、錄影、時限、SSO、vault、通知及健康檢查。

原創頁面以工作流程與風險決策為中心，不照抄商業 PAM 版面或只換名稱。
可見動作由後端回傳 capabilities，執行時仍再次授權。無權限、無資料、服務失聯、
等待審批及功能不支援是不同狀態，需各有明確提示。
未實作的功能用狀態說明，不呈現可點擊但無實際效果的按鈕；正式模式不載入 demo 資料。

所有新表單考慮鍵盤操作、手機、長名稱、多語、日期邊界、重送與重複點擊。
成功訊息只在後端已完成對應狀態轉移時顯示。排程中斷或通知僅入佇列時，顯示「處理中」。

17. 建議資料模型、交易與一致性
======================================================================

P01 的官方 MFA／錄影試點優先使用官方既有儲存方式，不先建立新的業務資料庫。
進入廠商、審批及 grant 階段後，因需要持久化自訂狀態機、交易及稽核，才新增 PAM
獨立邏輯資料庫與最小權限帳號。可共用同一 PostgreSQL 服務，不要求多一個 DB 容器。
PAM migration 不直接修改 Guacamole 原生表格；官方 MFA 的屬性保存是原生擴充行為，
部署前仍需說明及備份，不能把它描述成完全沒有資料寫入。
PAM runtime 不使用 DB superuser；migration、事件寫入與稽核讀取採不同的必要權限。

建議邏輯實體（不是已存在的 schema）：
installation：安裝實例 ID、版本、schema 版本及啟用 profile。
identity_link：身份來源、穩定 subject、Guacamole 對應、狀態與有效期。
vendor_org／vendor_membership：廠商、負責人、合約、人員關係及範圍。
asset_ref：data_source、原生 connection_id、版本、風險、擁有者與能力。
target_account_ref：帳號類型、資產、秘密引用及已確認的版本，不存明文密碼。
role_binding：主體、角色、資源範圍、條件與期限。
policy／policy_version：型別化規則、發布者、版本及生效狀態。
access_request／request_revision：申請內容、狀態、版本及必要的政策快照。
approval_step／approval_decision：指定角色／範圍、決定者、理由及不可覆寫的決定。
access_grant：核准範圍、有效期、session 條件、撤銷與版本。
launch_intent：短期 nonce 摘要、主體／session 綁定、grant、消耗狀態及期限。
session_lease：節點、tunnel 參照、grant、心跳、硬期限及中斷結果。
recording_index：session、provider、opaque path、狀態、完整性資料及保存期限。
audit_event／outbox／job：事件、可靠通知／工作及去重資料。
rotation_run：connector、帳號引用、版本、狀態與受保護的復原引用。

Guacamole ID 只當外部引用，不做跨資料庫 FK，也不以顯示名稱取代穩定 ID。
同一組織／實例範圍應有必要的複合唯一鍵與索引，防止不同來源 ID 撞號。
權限、審批、消耗啟動資格及容量扣除須有明確交易邊界、樂觀版本或鎖。
授權決定和事件 outbox 同交易；通知與遠端 API 採冪等重試。

敏感刪除以撤銷／封存與保留政策處理，不能把已存在的稽核關聯一起 cascade 刪除。
熱路徑每次 connect 都檢查權威狀態；若有快取，撤銷版本與最大有效期須有測試證據。
Worker 的工作處理採 DB 持有權及冪等狀態機，未量測前不增加訊息中介軟體。

18. API 與模組契約（原創草案，尚非原生端點）
======================================================================

以下是邏輯操作契約；實際 URL prefix 與已認證身份的取得方式由 G01 證明後決定。
不可直接把這些名稱寫進 UI，就宣稱 Guacamole 已支援。

GET    /pam/v1/me                         目前可信身份、組織、角色範圍及 capabilities。
GET    /pam/v1/assets                     可見／可申請資產與限制，不含秘密。
POST   /pam/v1/requests                   建立／送出申請，回傳版本與狀態。
GET    /pam/v1/requests/{id}               取得自己或有責任範圍的案件。
POST   /pam/v1/requests/{id}/cancel        合法狀態下取消，附 expected_version。
POST   /pam/v1/requests/{id}/decisions     核准／駁回，後端判斷決定者資格。
GET    /pam/v1/grants                     有權查看的有效／歷史授權。
POST   /pam/v1/grants/{id}/launch         產生短期啟動意圖，非目標密碼。
POST   /pam/v1/grants/{id}/revoke         撤銷及產生中斷工作，不假裝已同步全部關閉。
GET    /pam/v1/sessions                   範圍內的活動／歷史 session。
POST   /pam/v1/sessions/{id}/terminate    具權限者要求中斷，回傳 operation 狀態。
GET    /pam/v1/recordings/{id}             錄影索引與可用動作。
POST   /pam/v1/recordings/{id}/playback   短期受控播放資格，再次檢查範圍。
GET    /pam/v1/audit                      範圍內稽核查詢及分頁。
POST   /pam/v1/vendors/{id}/suspend       具授權者停用廠商，回傳受影響工作。

所有變更端點需 CSRF／身份防護、輸入驗證、範圍檢查及 correlation_id。
送件、決定、啟動及撤銷支援 idempotency key；同 key 不得產生不同權利。
建議錯誤：未認證、需再次驗證、範圍禁止、狀態衝突、輸入不合法、容量超限、
必要能力不支援及依賴不可用。HTTP status 與 application error code 分開定義。
回應不包含 SQL、stack trace、內部秘密、其他廠商是否存在或無權查看的資產細節。
串接官方 TOTP 時沿用其身份挑戰流程，不自行假設以上 API 可取代官方登入端點。

核心契約示意：
PolicyEngine.evaluate(principal, assetRef, grantRef, context, serverTime) → Decision。
Decision：allow／deny、原因碼、policy_version、必須落實的 obligations 與最早到期時間。
GrantService.reserveLaunch(...) → 一次性資格，需原子檢查容量及有效期。
SessionControl.terminate(sessionRef, reason, operationId) → 真實執行結果與節點狀態。
VaultProvider.getVersionedSecret(ref, purpose, correlationId) → 不可一般序列化的秘密型別。
RecordingStore.finalize／openAuthorized／purge → 狀態、範圍驗證與冪等結果。
AuditSink.append／export → event_id 去重及可驗證的交付結果。

Connector 要聲明 supported_versions、capabilities、timeout、重試／冪等特性與 health。
不允許廠商上傳任意伺服器腳本或動態 eval 政策；外掛安裝屬受信任管理平面的動作。

19. 部署設定與主題／安全模組分離
======================================================================

設定分三層：
A. 可進 Git 的範例／schema：服務名稱、功能開關說明、非機密的合理預設。
B. 每個安裝實例的設定：public URL、base path、compose 檔集合、磁碟路徑、節點及 provider。
C. 機密：資料庫、IdP、vault、郵件等憑證及加密金鑰，使用受保護的外部來源，不進 Git。

以下僅為本產品未來自訂的設定草案，不是 Guacamole 原生環境變數：
installation_id：首次設定生成並保存，不寫死在程式碼。
public_url：https://access.example.invalid；安裝時必須改成有效部署地址。
deployment_profile：demo_local／internal_pilot／external_enforced。
policy_mode：disabled／audit／enforce；audit 只供內部試點，不當作外包保護。
vendor_access_enabled：預設 false；完成外包最低驗收後才能開啟。
default_request_duration：建議 60 分鐘；最長 4 小時僅為待確認範例。
launch_ttl：建議 60 秒；max_sessions_per_vendor_user：建議 1。
active_revoke_target：建議 15 秒，需量測；recording_retention_days：建議 90，需確認。
recording_root、backup_root、pam_db_secret_file、vault_provider、audit_sink、trusted_proxies。

功能旗標只是組態，不取代安全檢查。external_enforced profile 缺少必要 adapter、MFA、
錄影能力或健康證據時，須拒絕外包新連線，不退回 password-only 或未控管模式。
模組本身遺失時無法靠該模組拒絕存取，需由部署啟動檢查／受保護入口及網路限制補足。

主題 JAR 保持純 CSS／JS／HTML；安全 adapter 使用不同名稱、namespace、設定與生命週期。
現有主題 import 會拒絕 Java 認證提供者；不得為安裝安全模組而放寬這個限制。
安全 JAR 由專用部署清單管理，只替換自己管理的檔案，不刪除其他擴充或繁體中文 JAR。

關鍵要求：所有重建 Web 的工具，都要使用同一份「完整有效的 Compose 設定集合」。
若 MFA 寫在 overlay，而主題 CLI 只使用 base compose，切換主題可能意外移除 MFA。
必須設計共同 deployment manifest／lock 或安全的設定遷移，並測試 switch、reset、
upgrade、restore 後 MFA／政策仍在。不得為加入 overlay 就盲目重設現有部署或多次重建。

Theme reset 只還原外觀，不停用 MFA、PAM gate、錄影或稽核。
安全模組停用是不同操作，須說明外包入口處置及降級狀態，不能借主題 reset 執行。
沒有必要時不重建 guacd／PostgreSQL，沒有任何升級流程可執行 down -v 或刪除既有 volume。

21. 發行、設定匯出與供應鏈
======================================================================

提供兩條使用路線：
原始碼：git clone <repository-url> → 閱讀 README／本計畫 → 設定 → 測試／建置。
一般安裝：下載可信 Release → 驗證校驗／簽章 → 互動設定或匯入實例設定 → 診斷。
尚未建立遠端 repository 時，文件使用 placeholder，不捏造下載網址或已發布狀態。

建議 Release 包含：版本限定的 PAM JAR、獨立主題 ZIP、必要 UI／CLI、
無機密 Compose／設定範例、migration、相容矩陣、LICENSE／NOTICE、SBOM、
SHA256SUMS、簽章或可信來源驗證資訊、升級及還原說明。
固定 archive 順序與時間戳；相同工具鏈／相同來源應可重現，公開工具鏈版本。
依賴和官方 image 採鎖定版本／digest；不能在正式安裝中使用未審查的 latest。

SHA-256 證明完整性，不證明發行者可信；需要簽章時，信任金鑰必須由另一可信途徑提供。
第三方主題 JS 可使用登入者的同源權限，不得因為它是視覺包就當作無風險資料檔。
安全 connector 是可執行程式，不能由外包帳號自行上傳／啟用。

設定匯出採 schemaVersion 與 capabilities，預設移除秘密、錄影及實例身份資料。
asset／identity 引用跨環境時須重新對應，不能匯入原機的 active grant、有效邀請或 session。
如需含秘密的移轉備份，使用獨立受控流程、加密、權限與復原演練，不夾在公開套件中。
離線安裝包另列所需 image／artifact 清單、授權及架構支援；未實測 ARM64 不宣稱支援。

22. 備份、復原、監控與營運
======================================================================

主題備份只包含視覺狀態，不等於 PAM／Guacamole／vault／錄影的完整備份。
完整營運備份需涵蓋：設定版本、PAM DB、必要的 Guacamole DB、MFA 恢復需求、
錄影索引／檔案、稽核 anchor、connector 引用及必要的受保護金鑰。
實際秘密與備份解密材料分開保存，權限與保存期可設定。

復原需對帳：未結申請、有效 grant、已死的 session、vault／目標輪替版本與錄影狀態。
不能只還原舊 DB 就把已離場廠商重新啟用，或讓已撤銷 grant 因時間回溯再次有效。
安全模組重大故障時先限制外部新連線，依明確程序保留獨立管理通道。
既有 session 的處置依策略與實際可控制範圍回報，不以成功 HTTP 回應冒充終止。

最低健康／監控項目：MFA／gate 載入證據、政策依賴可用、時鐘、DB schema、
錄影容量與失敗數、到期工作延遲、撤權未確認、outbox backlog、vault 失敗、
跨組織拒絕事件、疑似重放與例外設定變更。
Readiness 和 liveness 分開；依賴失聯的健康回應不得回傳帳密、完整連線參數或 token。
預設 stdout／結構化日誌只含必要識別碼、結果與原因，預先建立秘密遮罩與測試。

23. 技術驗證關卡（在承諾功能前完成）
======================================================================

G01：身份與新連線攔截。
在官方 1.6.0、真實 JDBC 身份下驗證 decorator、原生 URL、HTTP／WebSocket tunnel、
連線群組、活動連線加入、共享及重連；證明每條受控路徑都到達 gate。
確認身份／MFA／session 證據可從可信後端取得，完成 admission 綁定 POC。
交付來源檔與方法、sequence、拒絕案例及限制。若不通過，禁止對外提供審批／JIT 保證。

G02：撤銷與期限。
驗證 tunnel 關閉的實際效果、權限、節點生命週期、重啟／斷線與目標背景程序語義。
量測延遲並提出能承諾的 SLA；單節點通過不代表多節點通過。

G03：資料隔離與錄影。
驗證原生參數、歷史、錄影、共享、資產與使用者目錄的權限邊界。
廠商 A 不得看 B 的個資、事件、錄影或秘密；原生 API 也必須通過負面測試。

G04：部署與安全持續性。
測試所有工具使用同一份有效 Compose 設定；主題切換／reset／upgrade／restore 後
安全模組不消失。缺少 gate／壞掉的政策依賴時，外包入口採明確的 fail-closed 行為。

G05：保管庫與改密。
先完成版本化取密、秘密不外洩、無效版本拒絕，再做單一目標種類的輪替 saga。
未完成目標變更與 vault 失敗的復原測試，不可宣稱自動改密已可用。

24. 分階段交付與代理工作順序
======================================================================

P00 規格與相容性：本文件、角色／威脅模型、ADR、來源核對、G01～G04 的最小 POC。
交付可執行的隔離驗證及明確限制；不先畫一堆會假裝成功的 PAM 頁面。

P01 官方能力試點：HTTPS 條件、TOTP 綁定／復原、錄影／回放與容量管理。
交付可重現設定、預建依賴清單、啟用／還原工具及身份／錄影驗收。
優先完成，因官方已有基礎；此階段不把內部試點當作完整外包正式接入。

P02 原創身份與範圍：廠商、人員、內部負責人、角色範圍、資產／帳號引用與生命週期。
交付 schema／migration、API、UI 與跨廠商／到期測試，沿用既有身份不強迫重建帳號。

P03 原創審批及限時連線：狀態機、決定、grant、admission、connect gate、撤銷與硬期限。
交付直連旁路負面測試及活動 session 的真實處置。G01／G02 不通過不得部署此承諾。

P04 稽核與外包正式版：整合 request→grant→session→recording、查詢／匯出、
通知、保存、復原與完整外包退出演練。通過最低對外條件後才開啟 vendor access。

P05 保管庫與憑證注入：以一個受支持 provider 完成 F09／G05 前半，不同 provider
透過同一契約增加，先不追求一次支援所有廠牌。

P06 自動改密與目標提權：一種目標、一類帳號、一套復原流程先驗證，再逐一擴充。
此階段需另排程確認目標管理權、緊急通道與失敗處理，不在正式設備盲目試改密。

P07 發行硬化：乾淨 Git checkout、預建 Release、離線選項、跨路徑／平台矩陣、
供應鏈、備份復原、效能及升級演練。量測後才制定容量與多節點承諾。

每個工作項都附：需求 ID、範圍、角色／資料來源、依賴、變更檔案、API／schema、
失敗及回復方式、負面測試、交付物、未完成清單與部署影響。
預設以小型垂直切片完成真實流程，不以先堆滿空頁面作為進度。

25. 後續實作代理的工作指令
======================================================================

開始前：
1. 讀本文件、既有 README、架構、安裝／還原、測試與最新部署紀錄。

9. 機密不可進原始碼、範例、CLI 參數、日誌、截圖、快取、報表與 Release。
10. 若要新增後端服務／框架／儲存，先以 ADR 說明原生擴充不足的證據、成本與替代方案。

驗證與交付：
11. 對各角色、跨廠商、直接 URL／API、邊界時間、併發、依賴失敗與重啟測試。
12. 既有 1.1.0 主題及原生管理頁回歸通過；測試中斷工作階段不等於驗證所有目標行為。

26. 核心驗收矩陣與上線判定
======================================================================

A. 身份：密碼成功但缺 MFA 被拒絕；正確綁定可用；失去身份／合約即拒絕；復原可演練。
B. 廠商：A／B 相同顯示名稱也不撞資料；換 ID、資料來源或直接 API 都無法越界。
C. 審批：不能批准自己；失去角色不能核准；併發決定只有一個有效結果；修改需重審。
D. 授權：未生效、剛好到期、撤銷、超額、重放、換身份及不支援能力均被後端拒絕。
E. 旁路：原生 client URL、HTTP／WebSocket、重連、群組、共享及多 provider 不能繞過。
F. 工作階段：到期／撤銷可在承諾時間內確認中斷；失聯／重啟不會無限延長或誤殺他人。
G. 錄影：真實 RDP／SSH／VNC 目標可記錄與回放；權限隔離、儲存滿、破損與保留均測試。
H. 機密：瀏覽器、匯出、錯誤、日誌、截圖、Git 及 artifact 不含目標密碼／seed／token。
I. 稽核：變更有事件；重送不重複生權；誰看過／下載錄影可追溯；外部 anchor 能驗證。
J. 部署：乾淨環境、既有部署、自訂路徑／服務名；升級／還原及主題 reset 保留安全功能。
K. 復原：管理員裝置遺失、政策依賴失聯、備份還原、到期 jobs 重跑及失敗改密可處置。
L. 可攜：新 clone、預建 ZIP／JAR、校驗／簽章、設定遷移、無客戶資料與無編譯安裝。

建立 acceptance ledger，逐項記錄：要求、版本、測試方式、fixture／真實環境、結果、
證據位置與限制。未做真實目標握手就不能把該協定列為端到端通過。
外包正式上線需完成 A～L 的第一版範圍：I 至少具備完整事件及受控查詢／匯出，
L 至少具備乾淨 Git／預建安裝及安全設定；外部不可變儲存與離線／多架構可另外分級。
涉及憑證與輪替時，G05 及 H／K 的相關案例不可延後。
未具備多租戶、HA、不可變儲存或端點提權實測時，對外不宣稱已有這些能力。
